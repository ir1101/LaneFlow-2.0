Small documents wait

Most of a small file's time is spent waiting on S3 and DynamoDB over the network. Extra memory does not make waiting any faster, so the 3008 MB baseline pays for memory that sits idle. A 256 MB lane does the same work for a fraction of the cost.

Large documents compute

Extracting text from a large file is pure computation. Up to about 1769 MB, Lambda adds CPU in proportion to memory, so the job finishes sooner and the bill stays roughly level. Beyond that, a single-threaded job cannot use the extra CPU: in tuning, 3008 MB was no faster than 1769 MB and cost almost twice as much.

Tuned, not guessed

Each lane's memory comes from AWS Lambda Power Tuning. Every document size ran ten times at each setting, with the fastest and slowest fifth of runs discarded. The rule is the cheapest memory that extracts a document in under five seconds.

Orchestration decides it

Step Functions Standard bills USD 0.000025 for every step. Measured on the same runs, that would cost far more than routing saves. Express bills per run and per second, so the extra classification step is almost free.

04/04

How it is built

Every resource is defined in a single SAM template, so the whole system is created with one command and removed with another.

  1. CloudFront serves this site from a private S3 bucket and forwards /api calls to API Gateway, so the site and its API share one address.
  2. The website API signs a short-lived, PDF-only upload form of at most 25 MB for the KMS-encrypted upload bucket.
  3. The upload raises an S3 event. The validator checks the file really is a PDF and queues a job in SQS.
  4. The dispatcher starts one Express Step Functions run per job, named after the document so it can be traced.
  5. The classifier reads only the few kilobytes that hold the page count, scores pages and size, and a Choice state sends the file to the light (256 MB) or heavy (1024 MB) lane, sizes chosen by Power Tuning. Baseline runs skip the classifier and always use 3008 MB.
  6. Results go to DynamoDB, the text to the curated bucket, and SNS announces the outcome.
  7. A failed run is marked, moved to the dead letter queue and raises a CloudWatch alarm.
  8. The reconciler reads each function's billed duration from CloudWatch Logs and writes the actual cost back to DynamoDB.

Tear it down.

One command removes every resource in the stack, from the CloudFront distribution to the last log group, and another rebuilds the lot in about ten minutes.
